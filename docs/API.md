# REST contract — `/api/v1`

All requests/responses use JSON except multipart photo upload. Send `Accept: application/json`; authenticated calls send `Authorization: Bearer <token>`. Return validation errors as HTTP 422 `{message,errors:{field:[...]}}`, unauthenticated 401, forbidden 403, conflict 409, throttled 429. UUIDs are opaque. Times are UTC ISO-8601.

Rate limits: the API has a general 120 requests/minute limit; registration 5/minute, login 8/minute, password-forgot 3/minute, password-reset 5/minute, photo upload 10/minute, friend requests 10/minute, message sends 30/minute, reports 5/hour, matchmaking queue 5/minute, and call signaling 120/minute. Each route-specific limiter uses its own key prefix so it is not accidentally double-counted against the general throttle.

## Auth/account
- `POST /auth/register` `{identity,password,password_confirmation,terms_accepted:true}` → 201 `{data:{user:{id,identity,status:onboarding,profile},token}}`. `identity` accepts email or international phone. It starts a restricted onboarding account; it does not accept a self-asserted age checkbox as proof.
- `POST /me/onboarding/complete` (authenticated onboarding account) `{birth_date,name,username,country,languages[],interests[],bio?}` → 200 public profile and activates the account only if the submitted birth date indicates age 18+. This is a self-declared eligibility check, not identity verification. The current frontend discards the raw DOB and retains derived age only, so its onboarding adapter must be extended to securely submit DOB once; do not reconstruct a birth date from age.
- `POST /auth/login` `{identity,password}` → 200 `{data:{user,token}}`; generic credential errors.
- `POST /auth/logout` (auth) → 204 revoke current token/session; `GET /me` → private account + profile. Browser SPA clients use Sanctum's stateful HttpOnly session cookie after calling `/sanctum/csrf-cookie`; no bearer token is stored in browser storage. Non-browser clients may receive a Sanctum token. Suspended/banned users may log in only to receive appeal-only access; other authenticated profile/data routes require an active account.
- `POST /auth/password/forgot` `{identity}` → generic 202 (do not reveal account existence); email accounts receive Laravel broker reset messages; phone-only accounts need a configured verified SMS provider before phone reset can be offered. `POST /auth/password/reset` `{email,token,password,password_confirmation}` → 204; reset revokes all tokens.
- `PATCH /me/profile` `{name,username,country,languages[],interests[],bio,online}`. `POST /me/profile/photo` multipart `photo` (JPEG/PNG/WebP, size/dimensions limits, re-encoded, metadata stripped) → `{data:{photo_url}}`; `DELETE /me/profile/photo` → 204.
- `GET/PATCH /me/preferences` handles online, discovery, notification, request/message permissions and matching settings. Never expose email/DOB in public profiles.
- `GET /me/export` (active authenticated account, one request/hour) returns a downloadable JSON export of the account holder's private account/profile/preferences, relationships, notifications, reports/appeals, and messages in their own conversations; it does not disclose other accounts' login/contact data. Profile photo is represented by a short-lived signed link.
- `DELETE /me/account` `{password,confirmation:"DELETE"}` (active account, throttled) revokes tokens, removes photo/profile data and social state, deletes shared conversation history, erases DOB/contact data, and soft-deletes an anonymized UUID tombstone needed to retain case/audit references. Reports, decisions, appeals and admin audit records are retained for 365 days after resolution/creation; unresolved pending cases remain until resolved. The scheduler prunes eligible records after `MODERATION_RETENTION_DAYS` (default 365). This is a proposed operational retention default and requires privacy/legal review before production.

## Discovery/social
- `GET /profiles?search=&country=&region=&language=&interest=&online=&favorite=&page=&per_page=` → `{data:[profile],meta:{...}}`. Search only public fields; block filtering is bidirectional.
- `PUT/DELETE /me/favorites/{user_id}` → 204; `GET /me/favorites` paginated.
- `GET /friends` → friends; `GET /friend-requests?direction=incoming|outgoing`; `POST /friend-requests` `{user_id}` → 201; `POST /friend-requests/{id}/accept|decline|cancel`; `DELETE /friends/{user_id}`. Enforce relationship state and block rules.

## Messaging
- `GET /conversations?page=&per_page=` returns accessible conversations and unread counts.
- `POST /conversations` `{user_id}` → 201 (only allowed participants; blocked users forbidden).
- `GET /conversations/{id}/messages?before=&per_page=` returns chronological page; `POST /conversations/{id}/messages` `{text,client_message_id}` → 201 message status `sent` (queued for realtime delivery); `POST .../read` `{through_message_id}` updates read receipt. Idempotency key/client ID prevents duplicate sends. Message events broadcast only on authorized private conversation channels.

## Match/calls
- `PUT /matchmaking/preferences` `{mode:video|text,countries[],languages[],interests[]}`.
- `POST /matchmaking/queue` → 202 `{data:{queue_id,status:searching|matched,match?}}`; `GET /matchmaking/queue/{id}` polls only the current user's queue entry/result; `DELETE /matchmaking/queue/{id}` cancels. Redis queue coordination re-checks mutual block/status on pairing.
- `GET /matches/{id}` returns the caller's match status/profile; `POST /matches/{id}/accept`, `/skip`, and `/next` transition the match. Both participants must accept before a call can start. Match result and status publish private Reverb events.
- `POST /calls` `{match_id}` → 201 call session; `POST /calls/{id}/accept|end` manage lifecycle; `POST /calls/{id}/signals` `{type:offer|answer|ice-candidate, payload}` bounded payload relayed only to the other participant. `GET /calls/{id}/ice-servers` returns short-lived ICE/TURN config. No media stream endpoints exist.

## Notifications/safety/admin
- `GET /notifications?unread=true&page=`; `POST /notifications/{id}/read`; `POST /notifications/read-all`. Notification writes persist the inbox item and dispatch `notification.created` after database commit on the authenticated private `users.{id}` channel. Mark-one/read-all actions dispatch `notification.read` or `notification.read_all` after the read state commits. Payloads: `{notification:{id,kind,title,description,data,read,created_at}}`, `{id,read_at}`, or `{all:true,read_at}`. `notifications:false` keeps inbox records but suppresses realtime events; account state and preference are checked again before broadcast. Requires Reverb and a running queue worker.
- `POST /blocks` `{user_id}`; `DELETE /blocks/{user_id}`; `GET /blocks`.
- `POST /reports` `{user_id,category,details,context?}` → 201 pending report; categories include sexual misconduct, harassment, hate speech, threats, scam/fraud, suspected underage, spam, impersonation, other.
- Admin-only `/admin/reports`, `/admin/reports/{id}/decision` `{decision,notes,account_status?}`, `/admin/users?search=&status=`, `/admin/users/{id}/status` `{status:active|suspended|banned,reason}` and `/admin/audit`. Decisions are `resolved`, `dismissed`, or `actioned`; `actioned` requires `account_status: suspended|banned`, revokes the target user's tokens, and writes both report and account-status audit records. Admin actions are audited and cannot be invoked by ordinary accounts.
- `GET/POST /me/appeals` allows an authenticated suspended/banned account to read its own appeal history and submit one pending appeal (`reason` 30–5000 chars, optional `source_report_id`). The appeal-only login session/token cannot access normal active-account endpoints. One pending appeal per account; submission is limited to 3 per 7 days.
- Admin-only `GET /admin/appeals?status=pending|upheld|reinstated|dismissed` and `POST /admin/appeals/{id}/decision` `{decision:upheld|reinstated|dismissed,notes}`. Reinstatement restores active status, leaves existing sessions revoked, and writes audit records. Only moderators can decide; self-review is forbidden.

## Events (Reverb)
Private channels: `users.{id}` (notification, match status), `conversations.{id}.{channel_generation}` (new message/read receipt), `matches.{id}` (state), `calls.{id}` (signal only). Conversation list/create responses include `channel_generation`; subscribe using the returned generation. Channel authorization verifies active account, participant membership, current block status, and generation. Blocking or moderator status changes increment generation and broadcast `conversation.channel_rotated` to active participants' private user channels with `{conversation_id,channel_generation}`. On receipt, clients should unsubscribe from the old conversation channel, refetch conversation state, and subscribe using the current generation. Subsequent events publish only to the new channel, and queued events tied to the old generation are suppressed. This makes an already-open old subscription stale without relying on forced socket disconnect; clients reconcile via REST.

## Frontend adapter mapping
The frontend has a Laravel adapter in `src/services/laravel.ts`, selected when `NEXT_PUBLIC_API_BASE_URL` is configured (unless `NEXT_PUBLIC_SERVICE_ADAPTER=mock`). It implements existing auth/profile/discovery/matching/messaging/friends/notification/safety/admin service contracts and adds account export/deletion and appeal services. UUIDs map to string IDs, UTC timestamps to UI-local labels, and messages map sender IDs to `from`. `src/services/realtime.ts` uses Laravel Echo/Pusher protocol to subscribe to private user/conversation channels; the browser config contains only a public Reverb app key and uses cookie/CSRF authorization. The prototype call screen still does not capture or play audio/video; server call sessions/signaling do not constitute working media.
